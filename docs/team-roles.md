# 三人团队当前分工与并行迭代规则

本文是当前三人协作的事实来源，替代早期按 30 小时拆分的初始冲刺表。团队仍使用
GitHub Issue 记录问题与验收，分支承载修改，Pull Request（PR）承载 Review 和
交接；`main` 必须始终保持可运行、可演示。

当前分工方向成立：

- 一人负责后端生图 Prompt 架构与评测。
- 一人负责前端体验检查和已确认问题的实现。
- 一人负责产品走查、优先级与验收。

但“前后端分开调整”不等于三人互不沟通。以下三类内容必须共同冻结：

1. 用户主路径和本轮 P0 验收标准。
2. 前后端协议、示例数据和状态语义。
3. 最终联调所使用的 Commit、运行进程和回归清单。

如果缺少这三个交点，最常见的结果是：Prompt 效果变好但前端无法解释、前端增加
了后端没有的状态、产品不断插入新想法，最后只能在联调阶段集中返工。

## 1. 当前成熟度与本轮目标

当前项目是**已经接通前端、持久后端、真实空间理解和首次主效果图的集成原型**，
不是生产级家装服务。现阶段不再以扩展功能数量为第一目标，而是收敛为一条更清楚、
更稳定、更可解释的产品体验。

本轮目标：

```text
产品确认最值得修的 3 个 P0 体验问题
→ 前端在不复制业务规则的前提下完成体验调整
→ 后端把当前单一 `renderPrompt` 字符串组装升级为可版本化、可评测的架构
→ 使用同一组固定案例完成端到端联调
→ main 保持可演示，失败时仍能诚实降级
```

本轮范围外：

- React/Vite 等大规模技术栈迁移。
- 登录、支付、交易、真实抖音私有 API 和多用户生产能力。
- 为了一个截图重做 `DesignRequest`、`GenerationRun`、`PlanVersion` 等稳定对象。
- 把视觉观感、商品价格、结构安全或尺寸判断全部交给 Prompt。
- 在没有评测样例时反复凭感觉改 Prompt。

## 2. 对象、协议与规则所有权

现有稳定对象继续保持：

```text
SpaceVersion
→ DesignRequest（不可变输入快照）
→ GenerationRun（一次方案执行）
→ PlanAsset（稳定方案谱系）
→ PlanVersion（不可变结果版本）
→ AICard v1（前端组合视图）
```

所有权规则：

| 内容 | 唯一所有者 | 其他角色可以做什么 |
| --- | --- | --- |
| 用户问题、优先级、文案承诺、验收口径 | 产品 | 前端和后端指出成本、风险和不可实现之处 |
| 页面布局、交互、浏览器状态和 Adapter | 前端 | 产品验收，后端审核协议含义是否被误用 |
| Schema、API 状态、持久对象和确定性规则 | 后端 | 产品审核表达，前端审核是否可消费 |
| 生图 Prompt、模型参数、版本和评测 | 后端 | 产品评价效果，前端提供实际展示约束 |
| 合并、发布候选 Commit 和最终回归 | 项目发起人 `xbhmd0434` | 三人分别提供自己的验收证据 |

任何角色都不能复制另一角色拥有的规则：

- 前端不能自行重算价格、库存、预算、安全或尺寸结论。
- Prompt 不能覆盖后端已冻结的预算、不打孔、保留物和所有权规则。
- 产品不能用文案把 `fallback/demo` 结果描述成真实 Live 能力。
- `AICard` 是前端 DTO，不反向成为数据库事实模型。

## 3. A · 产品与验收负责人

### 3.1 核心职责

产品负责回答“为什么要改、先改什么、怎样算改好”，不负责直接指定实现细节。

1. 从当前真实运行版本完整走查主链路，不只看设计截图。
2. 把观察转成问题，而不是直接给界面解法。
3. 每轮最多选择 3 个 P0；其余进入 Backlog，不在开发中途插入。
4. 为正常、信息不足、生成较慢、失败降级和重新进入页面写出预期。
5. 审核 AI 能力、商品、素材和数据来源表述是否真实。
6. 在 PR 中按验收标准给出通过/不通过结论。

### 3.2 产品走查清单

从以下角度检查当前产品：

| 检查面 | 必须回答的问题 |
| --- | --- |
| 用户目标 | 用户进入后是否立即知道能获得什么结果？ |
| 主路径 | 是否存在两个同样突出的主按钮或不必要的分叉？ |
| 输入成本 | 上传、选择素材、预算和约束是否在需要时才出现？ |
| 等待体验 | 用户是否知道当前阶段、预计动作和能否取消/重试？ |
| 结果可信度 | 为什么这样设计、哪些内容来自 AI、哪些需要确认是否清楚？ |
| 调整闭环 | 改预算或风格后，图片、商品、价格和理由是否同步变化？ |
| 失败状态 | Live、Fallback、Demo 是否诚实区分且仍能继续演示？ |
| 再次进入 | 刷新或重启后，用户是否看见正确的已保存结果？ |

### 3.3 产品 Issue 交付格式

每个产品问题必须包含：

```text
问题：
用户证据或走查路径：
影响状态：
优先级：P0 / P1 / P2
期望结果：
不要求做什么：
可验证验收标准：
需要前端还是后端：
```

不接受“页面再高级一点”“Prompt 再准一点”这类无法验收的任务。

### 3.4 产品完成标准

- 本轮 P0 不超过 3 个，并说明排序理由。
- 每个 P0 都有明确范围外事项和 2～5 条可验证验收标准。
- 在同一个已记录 Commit 上完成 390px 与桌面宽度走查。
- 正常、`needs_input`、fallback 和失败四类结果都有产品结论。
- 体验修改冻结后不再临时加入新主路径。

## 4. B · 前端体验与实现负责人

### 4.1 代码所有权

- `apps/douyin-demo/**`：当前默认抖音宿主前端。
- `apps/web/**`：兼容 AICard 页面与共享静态素材。
- 前端 Adapter、浏览器状态、响应式、可访问性和控制台错误。
- 前端启动、页面烟雾测试和发布候选的浏览器验收。

前端不直接读取 `services/**`，也不把 Demo 页面字段当成新后端协议；所有响应必须
先经过现有 Adapter。

### 4.2 开工前先建状态矩阵

每个受影响页面至少检查：

| 状态 | 前端应有的行为 |
| --- | --- |
| 初始/空状态 | 有单一主行动，不伪造已识别内容 |
| 输入预览 | 用户能确认或取消，未保存内容不冒充正式资产 |
| 上传/生成中 | 阻止重复提交，阶段和退出后果清楚 |
| 成功 | 图片、商品、总价、步骤、来源和版本一致 |
| `needs_input` | 展示需要补充的信息，不误报为系统失败 |
| Fallback/Demo | 可以继续操作，但来源标记真实 |
| 超时/失败 | 可重试或回到稳定结果，不留下假成功状态 |
| 调整预览 | Apply/Cancel/失败回滚语义清楚 |
| 刷新/重启恢复 | 显示已保存版本，不恢复临时预览 |
| 3D 空/默认/已保存 | 双资产引用、变换和视角恢复一致 |

### 4.3 本轮工作

1. 记录当前基线截图和主路径视频，标明 Commit 与运行端口。
2. 对产品提出的问题给出最小前端方案和影响状态。
3. 先修 P0，再处理 P1；不借机重构无关页面。
4. 若后端 Prompt 改动不改变协议，前端只比较结果展示和来源。
5. 若确需新增字段，等待协议和 fixture 先合并，再修改 Adapter 和页面。
6. 每个 PR 提供修改前后截图、390px/1440px 结果和手动验收路径。

### 4.4 前端完成标准

- 产品指定的 P0 验收标准全部可复现。
- 390px 与 1440px 无阻断性溢出、空白层或控制台错误。
- Live、Fallback、Demo、超时和失败状态没有串台。
- 刷新后只恢复已保存状态，Cancel/失败不会污染当前版本。
- 前端没有密钥，也没有复制预算、安全、尺寸等后端规则。
- `npm.cmd run check` 和抖音前端专用检查通过。

## 5. C · 后端生图 Prompt 与评测负责人

### 5.1 代码所有权

- `services/orchestrator/**`
- `packages/contracts/**`
- `packages/validation/**`
- `examples/**`
- 生图 Prompt Builder、Provider Adapter、模型配置、评测、降级和安全边界。

后端同学本轮重点是**生图 Prompt 架构**，不是顺带重写所有 API 或方案状态机。

### 5.2 Prompt 架构边界

Prompt 只负责把已确认的结构化输入翻译成模型可执行的视觉指令。建议拆成以下层，
禁止在路由或 UI 文案中继续拼接第二套字符串：

```text
RenderPromptSpec（稳定用途与输入协议）
├─ system_invariants       模型角色、真实性和输出边界
├─ source_scene_facts      原空间、固定结构、保留物和可编辑区
├─ inspiration_intent      可迁移的风格、材质、色彩和氛围
├─ selected_plan           已由后端确定的商品、摆放和预算结果
├─ hard_constraints        不打孔、保留、尺寸和安全约束
├─ edit_instruction        本次要改变的区域和程度
├─ negative_constraints    明确禁止删除、移动、添加或伪造的内容
└─ provider_parameters     模型、尺寸、seed、强度、超时和响应上限
```

计划引入但尚未作为持久领域对象实现的评测概念：

- `PromptVersion`：不可变模板版本，记录模板、模型、参数和 Schema 版本。
- `EvaluationCase`：授权输入、预期不变量和人工评分维度。
- `EvaluationRun`：某版本在某组样例上的结果、耗时、失败与回退。

这些概念先以模块、fixture 和评测报告落地；除非确有跨重启查询需求，不要为了
“架构完整”立刻扩张数据库。

### 5.3 不可交给 Prompt 的规则

- 商品价格、库存、尺寸和来源。
- 预算总价和不打孔等硬约束是否通过。
- actor 所有权、私有媒体访问和删除。
- `DesignRequest`、`GenerationRun`、`PlanVersion` 状态转换。
- Live/Fallback/Demo 的真实来源标记。

模型输出必须经过 Schema、媒体和确定性规则校验后才能写入结果。

### 5.4 最小评测集

至少建立 8 个可重复案例：

1. 当前主案例：书桌角落焕新。
2. 明确保留桌面主体和显示器。
3. 不打孔约束。
4. 低预算导致商品减少。
5. 局部编辑，禁止改变非编辑区。
6. 信息不足，需要用户确认尺寸。
7. Provider 超时或 5xx。
8. 非法、过大或不符合协议的模型响应。

每次 Prompt 版本至少记录：

| 指标 | 验收方式 |
| --- | --- |
| 结构保持 | 固定家具和非编辑区没有被删除或大幅改变 |
| 方案一致 | 效果图与选定商品、摆放和风格一致 |
| 硬约束表达 | Prompt 包含结构化约束，最终仍由代码复核 |
| 可解释性 | 能追溯 Prompt 版本、模型、输入快照和降级原因 |
| 稳定性 | 8 个案例无协议崩溃，失败走同结构 fallback |
| 性能 | 记录耗时、超时、响应字节和回退率 |
| 成本 | 记录调用次数或供应方用量，不自动批量生成无用候选 |
| 隐私 | 原图、密钥和供应商原始正文不进入日志、Trace 或 AICard |

人工视觉评分可使用 1～5 分，但必须同时保留上述硬性通过/失败项；平均分不能掩盖
结构破坏或隐私失败。

### 5.5 后端完成标准

- Prompt 由单一 Builder 生成，并带可追溯版本。
- 相同 `DesignRequest` 和 Prompt 版本能说明为何产生当前指令。
- 模型输出不绕过 Schema、Repository 和 `packages/validation`。
- 8 个评测案例有结果记录，失败原因可分类。
- Provider 失败时主链路仍返回诚实的同协议 fallback。
- 没有在日志、事件、Trace 或提交内容中泄露密钥、原图或供应商正文。
- 后端自动测试、集成测试和一次授权真实调用通过。

## 6. 三人必须共同维护的冻结接口

前后端可以并行，但以下内容只能通过单独的 Contract PR 修改：

- `packages/contracts/**` 中的 Schema。
- `/api/v1` 请求、响应和错误语义。
- `AICard v1` 的已有字段含义。
- `source_mode`、`status`、`run.stage` 和失败/重试语义。
- fixture 中用于前端渲染的示例数据。

修改顺序：

1. 产品写清用户为什么需要这个变化和验收结果。
2. 后端提交向后兼容的 Schema、fixture 和测试。
3. 前端确认 Adapter 能覆盖所有状态。
4. 三方 Review 后先合并 Contract PR。
5. 前后端再分别实现，不在两个功能 PR 中各自发明字段。

纯 Prompt 内部改动如果不改变协议，可以独立进行，但仍要提供评测结果和一次前端
结果展示检查。

建议建立以下 4 个 Issue：

交付：

负责人：前端。

交付：

- Adapter/界面实现和前端测试。
- 390px、1440px、失败和刷新恢复验收。

阶段门：关闭后端时仍可用 fixture 完成相同交互；开启后端时无需另一套页面。

### Issue 3：`[Backend] 生图 Prompt v1 架构与评测`

负责人：后端。

交付：

阶段门：Prompt 改动能通过对比评测证明收益，而不是只展示一张最好看的图。

负责人：项目发起人协调，三人共同执行。

交付：

- 固定 Commit、启动命令和端口。
- Live、Fallback、Demo、`needs_input` 四条路径。
- 一次预算或风格调整后的版本一致性。
- 刷新/重启恢复不回归。
- 已知限制、演示档位和回滚 Commit。

阶段门：产品按验收标准确认，前端确认页面状态，后端确认协议和来源。

## 8. 协作节奏与交接门

一轮迭代按阶段门推进，不要求三人同时写代码：

| 阶段 | 产品 | 前端 | 后端 | 通过条件 |
| --- | --- | --- | --- | --- |
| Gate 0：基线 | 走主链路 | 记录页面/状态 | 记录接口/模型版本 | 三人看到同一 Commit 和运行版本 |
| Gate 1：冻结 | 确认最多 3 个 P0 | 给出状态影响 | 确认协议/Prompt 边界 | 范围与验收无分歧 |
| Gate 2：并行实现 | 回答验收问题 | 使用 fixture 开发 | 使用 API/评测独立验证 | 前后端都不等待对方即可测试 |
| Gate 3：联调 | 逐条验收 | 接真实响应 | 检查请求、日志和来源 | 四条关键状态通过 |
| Gate 4：候选版 | 冻结新想法 | 只修阻断问题 | 只修阻断问题 | 记录 Commit、回滚和已知限制 |

建议每天或每个工作段至少同步两次，每次只回答：

```text
当前 Commit：
已完成：
接下来：
阻塞：
是否改变协议：
需要谁在什么时候验收：
```

阻塞超过 30 分钟必须写入 Issue；不能以“另一位还没做完”为理由停工，前端使用
fixture，后端使用 API/评测脚本继续推进。

## 9. PR 与合并规则

- 功能开发不直接推送 `main`。
- 一个 PR 只解决一个主要问题。
- 产品文档、Contract、前端、后端分别建分支，不互相夹带大范围修改。
- Contract 变化必须由前端和后端共同 Review；用户路径变化必须由产品 Review。
- Prompt PR 必须附评测摘要，不提交原图、密钥或供应商完整响应。
- 前端 PR 必须附桌面/手机截图和状态清单。
- 合并前运行与改动相关的检查；最终集成运行 `npm.cmd run check` 和
  `npm.cmd run check:douyin-integration`。
- 合并后从 `main` 重启实际进程再验收，不能只看旧服务或浏览器缓存。
- 代码、配置、协议或行为变化同步更新 `HANDOFF.md`。

推荐分支名：

```text
docs/product-audit
feature/frontend-p0-polish
feature/render-prompt-v1
fix/integration-blockers
```

## 10. 联合回归矩阵

| 场景 | 产品验收 | 前端验收 | 后端验收 |
| --- | --- | --- | --- |
| 正常 Live 生成 | 结果有价值且表述真实 | 状态、图片、商品和版本一致 | Prompt 版本、模型和结果可追溯 |
| `needs_input` | 问题对用户可回答 | 不显示成系统崩溃 | run 语义正确，不创建假结果 |
| Provider 失败 | 用户仍能完成演示 | 明确 Fallback/Demo | 同协议降级，不泄露内部正文 |
| 调整预算/风格 | 变化符合用户意图 | Apply/Cancel/回滚正确 | 派生请求和新 PlanVersion 正确 |
| 刷新或重启 | 用户看到已保存结果 | 临时预览不被恢复 | SQLite 对象和版本可重读 |

## 11. 本轮 Definition of Done
