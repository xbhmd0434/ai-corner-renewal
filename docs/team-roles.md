## 共同责任

三人共同负责：

- `main` 始终可运行、可演示。
- 每次代码或行为变化同步更新 `HANDOFF.md`。
- 不提交密钥、真实用户数据和未授权素材。
- PR 描述包含影响、验收方式、截图和回滚方法。
- 比赛前共同完成一次无讲解演练和一次异常兜底演练。

## Issue 与 PR 规则

Issue 必须写：

- 用户问题或工程问题。
- 明确的范围外事项。
- 2～5 条可验证验收标准。
- 数据、隐私和素材影响。
- 负责人和预计完成时间。

分支命名：

```text
feature/douyin-user-flow
feature/room-profile-schema
feature/product-retrieval
fix/mobile-result-layout
docs/demo-script
```

PR 规则：

- 一个 PR 只解决一个主要问题。
- 默认需要另外一名成员批准。
- 跨所有权改动需要对应负责人批准。
- PR 合并前必须通过 `npm run check`。
- 禁止直接向 `main` 推送功能开发。

## 两周建议排期

### 第 1 周：接轨抖音与工程化

| 成员 | 交付 |
| --- | --- |
| A | 用户模式流程、首屏信息裁剪、验收案例 |
| B | Vite/React 迁移、模式切换、部署预览 |
| C | JSON Schema、规则校验、演示数据规范化 |

周验收：用户能在抖音原生轻流程中完成“圈选—补充约束—看结果”，评委仍可展开完整 AI 过程。

### 第 2 周：接入一项真实能力

| 成员 | 交付 |
| --- | --- |
| A | 5～10 人快速可用性测试与演示脚本 |
| B | API 状态、错误降级、E2E 测试 |
| C | 真实空间理解接口、10 组评测结果 |

周验收：至少 10 张不同书桌图片能输出合法 `RoomProfile`；低置信度时会追问或降级。

## 每周节奏

- 周一：确定本周唯一演示目标和验收标准。
- 周三：三人走一次主路径，提前暴露接口和素材问题。
- 周五：合并稳定版本，更新交接文档和演示录像。
- 比赛前 48 小时：冻结新功能，只修演示阻断问题。
