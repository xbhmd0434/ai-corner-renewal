# 三人团队 · 30 小时黑客松分工与交接

本文是本轮黑客松的执行依据。计时统一使用 `T+小时`：`T+0` 是三人确认本文并开始工作的时刻，`T+27` 冻结新功能，`T+30` 完成最终提交。

团队只使用 GitHub 仓库作为事实来源，不额外依赖 Notion、飞书或 Jira。Issue 记录任务和阻塞，分支承载修改，Pull Request（PR）承载验收与交接，`main` 始终保持可运行、可演示。

没有 GitHub 协作经验时，统一使用 [`ai-github-playbook.md`](ai-github-playbook.md) 中的提示词，不自行发明另一套提交或合并流程。

## 1. 本轮唯一目标

在 30 小时内交付一条可以从头演示、接口失败也不会中断的主链路：

```text
抖音内容圈选
→ 搬进我家
→ 上传或选择房间
→ 填写预算、不打孔、保留家具等约束
→ AI 理解空间
→ 生成适配方案
→ 全屏查看前后效果
→ 展开商品清单与教程内容
→ 将预算压到 300 元并重新组合
→ 展开评委模式查看 AI 依据
```

必须保留三个体验记忆点：

1. 圈选内容后“一键搬进我家”。
2. 改造前后拖动对比。
3. “预算压到 300 元”后，商品组合和总价真实变化。

## 2. 完成口径与真实性边界

本轮要完成的是“可稳定演示的集成原型”，不是生产级家装服务。

| 能力 | 本轮完成口径 |
| --- | --- |
| 抖音入口 | 使用公开、授权或自制的演示内容复刻交互，不宣称已接入抖音私有 API |
| 空间理解 | 至少一次真实多模态调用，把房间图转换为合法 `RoomProfile` |
| 灵感、商品与教程 | 使用有来源说明的 Demo 数据，并在界面或文档中标明演示属性 |
| 预算与硬约束 | 使用确定性代码校验，不能只靠 Prompt 或前端文案 |
| 效果图 | 主案例使用预生成效果图；不要求任意图片实时生成 |
| 服务失败 | 自动返回同结构 Demo `AICard`，主链路仍能演示 |
| 评委说明 | 用户模式保持轻量，完整依据通过“查看 AI 过程”按需展开 |

比赛期间不做：

- React/Vite 迁移或大规模技术栈改造。
- 登录、支付、购物车、数据库和多用户系统。
- 真实抖音账号、交易、库存或私有内容接口。
- 任意房间的厘米级测量和施工级建议。
- 多空间长期记忆、连续视频理解和通用实时效果图生成。

这些能力进入赛后 Backlog，不得占用 `T+27` 前的主链路时间。

首次协作时填写姓名和 GitHub 账号。公开仓库不自动赋予写权限，仓库所有者仍需在 GitHub 中邀请另外两位成员成为 Collaborator。

| 角色 | 姓名 | GitHub 账号 | 独占所有权 |
| --- | --- | --- | --- |
| A · 产品、验收与路演总控 | 待填写 | 待填写 | 范围、用户路径、素材、验收、演示 |
| B · 前端与发布负责人 | 待填写 | 待填写 | `apps/web/**`、浏览器状态、部署 |
| C · 后端、AI 与协议负责人 | 待填写 | 待填写 | `packages/**`、`services/**`、`examples/**` |

项目发起人 `xbhmd0434` 暂时负责仓库权限、PR 合并和最终版本标记。角色所有权决定谁必须 Review，不代表其他成员不能提出建议。

### 稳定对象与规则归属

- `RoomProfile`：空间事实和不确定性。
- `InspirationProfile`：从内容提取的可迁移风格元素。
- `UserConstraints`：预算、保留项和安装限制。
- `DesignPlan`：商品、摆放、步骤、价格和效果图引用。
- `ValidationReport`：预算、结构、尺寸、可购买性和安全校验。
- `AICard`：前端消费的组合视图，不是底层事实来源。

C 拥有 Schema 和确定性规则，B 只呈现结构化结果，A 决定用户承诺和验收口径。任何一方都不能把同一业务规则复制到自己的模块中。

## 4. A · 产品、验收与路演总控

### `T+0～T+1` 必须完成

1. 冻结唯一主案例为“书桌角落焕新”。
2. 冻结唯一主入口为“圈选内容 → 搬进我家”。
3. 确认用户模式首屏只展示：
   - 前后效果。
   - 方案名与一句理由。
   - 总价。
   - 三个约束标签。
   - 商品、教程和查看 AI 过程三个行动入口。
4. 提供一张房间图、一条灵感内容、6 个商品和 3 条教程素材。
5. 为正常、信息不足、预算过低和接口失败四种情况写出验收结果。

### `T+1～T+24` 持续负责

- 创建并维护总 Issue、任务清单和阻塞状态。
- 审核所有改变用户路径、文案承诺、素材用途和抖音生态表达的 PR。
- 每两小时从入口完整走一遍，不只看单页截图。
- 新想法只进入 Backlog；只有会阻断主链路的 P0 问题可以插入开发。
- 在 `T+19` 前完成 5 名体验者的快速测试，记录完成率和首个卡点。
- 在 `T+24` 前完成三分钟演示脚本、异常兜底脚本和答辩问答。
- 在 `T+27` 前完成一次无讲解走查和一次断网/接口失败演练。

### 验收标准

- 不看讲解，体验者能理解“为什么这个内容适合我的空间”。
- 用户模式的每一屏只有一个主要行动。
- 所有商品、内容和 AI 能力表述都没有虚构平台接入。
- 演示者能在三分钟内完成主链路，并在失败时切换到兜底。

A 不直接修改 `apps/web/**`、`packages/**` 或 `services/**`；需要修改时在对应 Issue 中描述验收结果并通知所有者。

## 5. B · 前端与发布负责人

### 所有权

- `apps/web/**`
- 浏览器交互状态、上传预览、模式切换和错误降级。
- 响应式、可访问性、兼容性、性能和部署版本验证。
- Mock/Live 数据适配层。

### `T+0～T+7`：先打通 Mock 链路

1. 保留当前静态 H5 技术栈，不进行 React/Vite 迁移。
2. 根据 C 提供的 `examples/aicard.demo.json` 渲染结果，不等待真实接口。
3. 增加两种展示模式：
   - 用户模式：抖音原生轻流程和全屏结果。
   - 评委模式：展开当前完整诊断、规划和校验依据。
4. 保留并完善圈选灵感、前后拖动对比和预算重组。
5. 实现上传中、生成中、成功、信息不足、超时和失败状态。

`T+7` 验收：后端完全关闭时，仍能从入口走到最终 Demo 结果。

### `T+7～T+19`：接入真实接口

1. 通过单一适配器在 `mock` 和 `live` 数据源间切换。
2. 接入：
   - `GET /api/health`
   - `POST /api/generate`
   - `POST /api/revise`
3. 调用超时或响应不合法时自动降级到 Demo `AICard`，同时给出诚实提示。
4. “压到 300 元”必须更新商品列表、删除或替换理由、总价和校验状态，不能只改标题。
5. 手机宽度下完成完整操作，不能依赖 Hover。

### `T+19～T+27`：发布

- 修复联调和移动端阻断问题。
- 运行 `npm run check` 并完成手动验收。
- 提供线上地址和可离线运行的源码版本。
- 记录线上 Commit SHA，清缓存后再验证一次。
- 配合 A 录制完整演示视频。

### 验收标准

- 390px 和 1440px 下无阻断性溢出或控制台错误。
- Mock、Live、超时和失败四条路径都可以返回结果。
- 前端不包含密钥，也不自行计算后端拥有的业务规则。
- 切换方案时图片、商品、价格、步骤和校验保持一致。

## 6. C · 后端、AI 与协议负责人

### 所有权

- `packages/contracts/**`
- `packages/validation/**`
- `services/orchestrator/**`
- `examples/**`
- Schema、Prompt、模型适配、规则校验、评测和失败兜底。

### `T+0～T+1`：先交协议

1. 定义 `AICard v1` 及六个核心对象的最小字段。
2. 提交 `examples/aicard.demo.json`，包含前端完整渲染所需内容。
3. 与 A 确认字段表达，与 B 确认字段可渲染。
4. 协议通过 Review 后先单独合并，避免前后端互相等待。

协议一旦合并，除修复阻断问题外不得随意重命名字段。新增字段优先保持向后兼容。

### `T+1～T+7`：API 与规则骨架

实现：

```text
GET  /api/health
POST /api/generate
POST /api/revise
```

约定：

- `generate` 接收房间图、灵感引用和 `UserConstraints`。
- `generate` 返回合法 `AICard`。
- `revise` 接收原 `plan_id` 和新预算，返回新版本 `DesignPlan`、`ValidationReport` 与组合后的 `AICard`。
- 后端为每次请求生成 `request_id`，便于演示时定位失败。
- `.env` 永不提交，只提交不含秘密的 `.env.example`。

`T+7` 验收：不调用真实模型时，API 也能稳定返回 Demo `AICard`；预算和不打孔规则有自动测试。

### `T+7～T+19`：接入真实空间理解

1. 接入一个团队已有访问权限的多模态模型。
2. 将房间图片转换为合法 `RoomProfile`，至少包含：
   - 空间类型。
   - 固定家具。
   - 可编辑区域。
   - 采光方向及置信度。
   - 不确定项和需要用户确认的字段。
3. 模型只负责提取和建议；预算、不打孔、保留家具等硬约束由代码复核。
4. 建立至少 5 个正常输入和 3 个异常输入夹具。
5. 记录主案例调用耗时、失败原因和降级次数。

### 验收标准

- 主案例真实调用能输出符合 Schema 的 `RoomProfile`。
- 非法模型输出会被拒绝、修复或降级，不能直接传给前端。
- 预算调整后总价不超过目标，且校验报告与商品组合一致。
- 模型或网络失败时，接口仍返回同版本 Schema 的 Demo 数据。

## 7. 前后端冻结协议

`AICard` 至少包含：

```json
{
  "schema_version": "1.0",
  "request_id": "req-demo-001",
  "source_mode": "live_or_demo",
  "room_profile": {},
  "inspiration_profile": {},
  "constraints": {},
  "plan": {},
  "validation": {},
  "products": [],
  "tutorials": [],
  "render": {
    "before_ref": "",
    "after_ref": ""
  }
}
```

协作顺序：

1. C 提交 Schema 与示例。
2. A 审核产品表达和数据来源。
3. B 审核能否覆盖全部界面状态。
4. 三方通过后合并协议 PR。
5. B 和 C 分别在自己的目录继续开发。

如果接口尚未完成，B 使用固定示例；如果前端尚未完成，C 使用 API 测试验证响应。禁止以“对方还没做完”为由停工。

## 10. PR、合并与同步规则

- `main` 始终保持可运行、可演示。
- 禁止直接向 `main` 推送功能开发。
- 开工两小时内建立 Draft PR，让其他成员能提前看到方向。
- 一个 PR 只解决一个主要问题，优先小步合并。
- 协议 PR 最先合并；前后端功能 PR 不互相夹带修改。
- 跨所有权修改必须由对应负责人批准。
- 合并前必须运行 `npm run check`。
- PR 描述必须写清影响、验收方式、截图或接口样例、失败降级和回滚方式。
- 代码、行为、配置或架构变化必须同步更新 `HANDOFF.md`。
- `T+27` 后禁止协议和功能变更，只允许修复演示阻断问题。

每两小时同步一次，每次不超过十分钟，只回答：

```text
已完成：
接下来：
阻塞：
是否改变 AICard：
是否影响三分钟演示：
```

阻塞超过 30 分钟必须写入对应 Issue 并通知交接对象，不能独自等待。

## 11. 演示降级等级

从高到低准备三档，A 在演示前明确当前使用哪一档：

1. **Live 完整版**：真实空间理解、规则校验和前端结果全部在线运行。
2. **Live 理解 + 预生成结果**：真实输出 `RoomProfile`，效果图和商品方案使用固定样例。
3. **离线 Demo**：使用固定 `AICard` 和本地素材完整走主链路。

任何降级都必须保持相同 Schema 和相同交互顺序。不得在演示中临时切换另一套页面或另一份数据结构。
