# 用 AI 完成 GitHub 协作

本文面向没有 GitHub 协作经验的三人团队。团队成员只需要理解：

```text
Issue 是任务单
→ Branch 是个人工作区
→ Pull Request 是交作业和 Review
→ main 是始终可演示的稳定版本
```

具体的检查、建分支、修改、测试、提交、推送和创建 PR 可以交给 AI。合并 PR、公开数据和删除重要内容仍需人明确确认。

## 1. 安全底线

- 每个人在自己的电脑上单独克隆仓库，不共享同一个本地目录。
- 功能开发不直接提交到 `main`。
- AI 默认只创建 Draft PR，不自行合并。
- 禁止 `git push --force` 和 `git reset --hard`。
- 不提交 `.env`、令牌、Cookie、私钥、真实用户数据和内部日志。
- 不把模拟数据描述成真实抖音能力。
- 涉及代码、行为、配置、资产或架构变化时同步更新 `HANDOFF.md`。
- 不要把访问令牌粘贴给 AI；使用 `gh auth login` 在本机授权。

## 2. 第一次加入项目

接受仓库邀请后，将下面的提示词交给 AI：

```text
请帮我加入并初始化这个项目：

仓库：https://github.com/xbhmd0434/ai-corner-renewal

先检查 GitHub CLI 登录状态；如果没有登录，引导我运行 gh auth login，
不要让我把令牌粘贴到聊天中。

然后：
1. 把仓库克隆到我的工作目录。
2. 确认远程仓库、main 分支和 GitHub 身份。
3. 运行 npm run check。
4. 完整阅读 README.md、HANDOFF.md、docs/architecture.md 和 docs/team-roles.md。
5. 根据 docs/team-roles.md 告诉我负责哪些目录、对象和 Review。
6. 暂时不要修改代码、创建分支或提交。
```

## 3. 万能开发提示词

三个人接到明确任务后都可以使用：

```text
请在当前 ai-corner-renewal 仓库完成以下任务：

【任务】
在这里写具体需求。

【验收标准】
1.
2.
3.

请执行完整 GitHub 协作流程：

1. 阅读 README.md、HANDOFF.md、docs/architecture.md 和 docs/team-roles.md。
2. 检查当前仓库、分支、远程地址和工作区状态。
3. 确认本地没有混入其他人的未提交修改。
4. 从最新 main 创建合适的 feature/、fix/ 或 docs/ 分支。
5. 如果没有对应 Issue，先创建 Issue，写清范围、范围外事项和验收标准。
6. 实现任务，不修改无关文件，不覆盖其他人的工作。
7. 完成必要测试，至少运行 npm run check。
8. 检查是否涉及隐私、密钥、模拟数据、抖音品牌或素材版权。
9. 如果代码、行为、配置、资产或架构变化，更新 HANDOFF.md。
10. 自查完整 diff，说明改了什么、没改什么、有哪些限制。
11. 提交并推送当前分支。
12. 创建 Draft Pull Request，关联 Issue，写清变化、验证、截图和风险。
13. 不要合并 PR，等待另一名成员 Review。

禁止：
- 直接向 main 提交功能代码
- git push --force
- git reset --hard
- 提交 .env、令牌、Cookie 或真实用户数据
- 把模拟数据描述成真实抖音能力
```

## 4. 产品与体验负责人

```text
你现在作为本项目的“产品与体验负责人”工作。

请先阅读 docs/team-roles.md 和 docs/product-spec.md。

任务：
【填写要讨论或设计的产品问题】

请完成：
1. 明确用户是谁、在哪个抖音场景触发、唯一主目标是什么。
2. 区分用户模式与评委模式。
3. 列出正常、信息不足、预算过低三类状态。
4. 把需求写成 GitHub Issue，包含范围外事项和可验证验收标准。
5. 如果修改产品文档，创建 docs/ 分支、更新文档并开 Draft PR。
6. 不替前端或 AI 负责人决定实现细节。
7. 指出哪些文案属于真实能力，哪些必须标记为演示或估算。
```

## 5. 前端与工程负责人

```text
你现在作为本项目的“前端与工程负责人”工作。

请先阅读对应 Issue、HANDOFF.md、docs/architecture.md 和 docs/team-roles.md。

任务：
【填写前端任务或 Issue 编号】

要求：
1. 从最新 main 创建 feature/ 或 fix/ 分支。
2. 先枚举页面状态、交互转换、移动端和异常状态。
3. 前端只消费结构化数据，不在组件里复制预算、尺寸和安全规则。
4. 保持用户模式轻量，同时保留评委查看 AI 过程的入口。
5. 完成桌面端和 390px 移动端验证。
6. 运行 npm run check。
7. 更新 HANDOFF.md。
8. 提交、推送并创建 Draft PR。
9. 在 PR 中附修改前后截图和手动验收结果。
10. 不要自行合并。
```

## 6. AI 与数据负责人

```text
你现在作为本项目的“AI 与数据负责人”工作。

请先阅读对应 Issue、HANDOFF.md、docs/architecture.md 和 docs/team-roles.md。

任务：
【填写 AI、Schema、数据或校验任务】

要求：
1. 明确修改属于 RoomProfile、InspirationProfile、UserConstraints、
   DesignPlan、ValidationReport 或 AICard 中的哪一个对象。
2. 区分稳定事实、模型估算、用户确认和演示数据。
3. 定义输入、输出、置信度、不确定项和失败降级。
4. 确定性预算、尺寸和安全规则不能只存在于 Prompt。
5. 为新增协议提供合法示例、异常示例和测试。
6. 不提交真实平台数据、密钥或未授权素材。
7. 运行 npm run check。
8. 更新架构和 HANDOFF.md。
9. 提交、推送并创建 Draft PR。
10. 不要自行合并。
```

## 7. 审查别人的 PR

另一名成员收到 PR 后，可以先让 AI 审查：

```text
请审查仓库 xbhmd0434/ai-corner-renewal 的 PR #【编号】。

这次只做审查，不要修改代码、提交或合并。

请：
1. 阅读对应 Issue、PR 描述和完整 diff。
2. 检查实现是否满足验收标准。
3. 检查是否破坏用户流程、移动端、预算调整或保存状态。
4. 检查对象模型和模块所有权。
5. 检查密钥、隐私、模拟数据、抖音品牌和素材版权风险。
6. 检查测试和 HANDOFF.md 是否同步。
7. 按 P0 阻断、P1 应修、P2 建议分类输出问题。
8. 每个问题指出具体文件和行号，并说明如何复现或修复。
9. 如果没有阻断问题，明确说明可以批准，但不要替我合并。
```

## 8. 处理 Review 意见

```text
请处理当前 PR #【编号】中的所有未解决 Review 意见。

要求：
1. 逐条读取评论，判断是必须修改、需要解释还是不应采纳。
2. 先告诉我处理计划。
3. 修改时不要扩大 PR 范围。
4. 补充或更新测试。
5. 更新 HANDOFF.md。
6. 运行 npm run check。
7. 提交并推送当前 PR 分支。
8. 逐条回复 Review 评论，说明改了什么。
9. 不要合并 PR。
```

## 9. CI 失败

```text
当前 PR #【编号】的 GitHub Actions 失败了。

请：
1. 使用 GitHub CLI 查看失败检查和完整 Actions 日志。
2. 找到第一个真正的根因，不要只处理最后一条连锁报错。
3. 说明是代码、配置、环境还是测试问题。
4. 在当前 PR 分支实施最小修复。
5. 本地重新运行对应检查。
6. 提交并推送修复。
7. 等待远程 CI，确认通过后再汇报。
8. 不要关闭检查、删除测试或降低验证标准来绕过失败。
```

## 10. 合并 PR

只有团队确认后才使用：

```text
请检查 PR #【编号】是否可以合并。

合并条件：
1. 验收标准全部满足。
2. GitHub Actions 全部通过。
3. 没有未解决的 P0/P1 Review。
4. HANDOFF.md 已同步。
5. 没有密钥、隐私和素材许可风险。
6. 分支没有与 main 冲突。

如果全部满足，使用 squash merge 合并，并删除远程功能分支。
如果任何条件不满足，停止合并并告诉我缺少什么。
合并后同步本地 main，并汇报最终 Commit 和仓库状态。
```

## 11. 每日项目状态

仓库负责人可以每天使用：

```text
请检查 GitHub 仓库 xbhmd0434/ai-corner-renewal 的当前状态。

汇总：
1. 开放的 Issue，按优先级和负责人分组。
2. 开放的 PR，说明等待开发、等待 Review、CI 失败或可合并。
3. 最近一次 GitHub Actions 状态。
4. 是否有长期无人处理或范围过大的任务。
5. 按三人的角色给出今天最合理的任务分配。
6. 不要修改仓库，只输出简短行动清单。
```

## 12. 冲突与回滚

发生合并冲突时：

```text
当前分支与 main 存在冲突。

请先解释冲突涉及哪些文件、双方分别修改了什么，以及推荐保留哪一部分。
不要使用 git reset --hard，不要覆盖未提交工作。
在我确认方案后解决冲突，重新运行 npm run check，再提交并推送。
```

线上或稳定版本出现问题时：

```text
请定位造成问题的 Pull Request 或 Commit。
不要重写 main 历史，不要强制推送。
使用 git revert 创建可审查的回滚提交，通过新的 PR 恢复稳定版本。
在 PR 中写清影响、根因、验证方式和后续修复建议。
```

## 13. 推荐人工确认点

AI 工作过程中出现以下情况必须暂停并询问人：

- 是否公开仓库、数据或素材。
- 是否合并 PR 或发布版本。
- 是否删除、覆盖或迁移重要数据。
- 需求存在两种会显著改变产品方向的解释。
- 修改真实接口权限、密钥、收费服务或生产配置。
- Review 意见与产品验收标准冲突。
